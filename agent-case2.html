한 줄 요약: 이번엔 어떤 일꾼이었을까?설명서를 쓰고, 직접 만들고, 검사받고, 사람과 같이 현장에서 고쳤어요

AI 에이전트 11장 · 전체 흐름 →

사흘(2026년 9월 26~28일) 동안 받은 부탁은 30개가 넘어요. 처음엔 "어떻게 하면 돼?"였는데, 끝날 때는 이런 것들이 실제로 돌아가고 있었어요.

  • 방문자 화면: 실시간 카트 지도, 지나온 경로, 판매 히트맵, 안내 챗봇, 남은 가챠 수량, 공지 배너, "여기로 와 주세요" 요청과 진행 안내
  • 운전자 화면: 위치 보내기, 가챠 판매 기록, 지금 갈 곳 추천, 요청이 몰린 곳, 가는 중 / 도착 / 못 가요 버튼
  • 설명서: 처음부터 끝까지 따라 할 수 있는 가이드 문서
🧒 비유: 실전 사례 1이 "숙제를 대신 정리해 준 친구"였다면, 이번에는 같이 모둠 과제를 한 친구예요. 친구(사람)는 운동장(캠퍼스)에 나가 직접 뛰어 보고, AI는 교실에서 설계도를 그리고 고쳤어요. 서로 결과를 주고받으면서 완성했어요.
01

부탁 알아듣기프롬프트 · 입구 검사 · 트랜스포머의 주목

FIRST PROMPT"카트로 캠퍼스를 돌아다니며 상품을 팔 거야. 내가 돌아다니는 경로를 사람들이 내 홈페이지에서 볼 수 있게 하고 싶어. 어떻게 하면 될지 알려 주고 파일로 저장해 줘!"

프롬프트 11장 · 프롬프트 → 에이전트 → 답변 →

첫 부탁은 "방법을 알려 줘"였어요. 그래서 바로 코드를 고치지 않고 설명서(가이드 문서)부터 썼어요. 그다음 "실제로 합쳐 줘", "검수해 줘", "기능 추가해 줘"처럼 부탁이 하나씩 이어졌고, 그때마다 할 일의 크기를 부탁에 맞췄어요.

🧒 비유: 친구가 "라면 어떻게 끓여?"라고 물으면 요리법을 알려 주고, "끓여 줘"라고 하면 그때 직접 끓여 주는 것이에요.

입구 검사 (가드레일) 10장 · 질문에 답하는 과정 →

답하기 전에 홈페이지를 직접 열어 봤어요. 부탁에 적힌 주소의 10장 자리에는 이미 "ChatGPT는 어떻게 작동할까" 설명이 있었어요. 그 내용을 덮어쓰지 않고, 카트 지도를 새 칸으로 만들자고 제안했어요.

정말 사람이 정해야 하는 것만 물었어요. 예를 들면 "Firebase 프로젝트를 둘 중 어느 것으로 쓸까요?", "AI 답변은 돈이 드는데 쓸까요?" 같은 질문이에요.

🧒 비유: 게시판에 그림을 붙이기 전에 그 자리에 누가 먼저 붙인 그림이 있는지 확인하는 것이에요.

트랜스포머의 주목 (Attention) 10장 · 생성형 AI 지도 →

긴 부탁에서 중요한 단어에 주목했어요. "경희대 국제캠퍼스", "자체 제작 카트", "경로", "사람들이 볼 수 있게". 그래서 지도 첫 화면을 캠퍼스에 맞추고, 지나온 길을 선으로 그리고, 누구나 로그인 없이 볼 수 있게 설계했어요.

🧒 비유: 숙제 안내문에서 형광펜으로 칠한 단어만 다시 읽는 것이에요.
02

설계도 그리기클라이언트·서버 · HTTPS · API와 SDK · 데이터베이스 종류

① 카트의 폰운전자 페이지가 GPS로 위치를 재서 3초마다 보내요
② Firebase (저장소)위치, 경로, 판매, 요청을 실시간으로 보관해요
③ 홈페이지 지도방문자 화면에 카트와 경로를 그려요

클라이언트와 서버 1장 · 클라이언트와 서버 →

원래 홈페이지는 파일만 내주는 서버라서, 카트 위치처럼 계속 바뀌는 값을 들고 있을 곳이 없었어요. 그래서 위치를 받아 두는 실시간 저장소(Firebase)를 가운데에 두었어요. 카트의 폰과 방문자의 브라우저는 둘 다 손님(클라이언트)이에요.

🧒 비유: 카트(보내는 손님)와 방문자(보는 손님)가 직접 만나지 않고 교실 게시판(저장소)을 통해 소식을 주고받는 거예요.

HTTPS 1장 · HTTPS →

폰의 위치 기능은 자물쇠가 걸린 주소(https)에서만 쓸 수 있어요. 사이트가 처음부터 https로 열려서 바로 쓸 수 있었고, 설명서에도 "https 주소에서 열어야 해요"라고 적어 두었어요.

🧒 비유: 내 위치 같은 비밀 편지는 봉투를 붙여야만 보낼 수 있다는 규칙이에요.

API와 SDK 2장 · API와 SDK →

지도는 Leaflet, 저장소는 Firebase 도구 상자(SDK)를 빌려 썼어요. 처음부터 다 만들지 않고, 검증된 도구를 조립했어요.

🧒 비유: 레고로 집을 지을 때 바퀴나 창문 블록은 이미 만들어진 걸 쓰는 것이에요.

데이터베이스 종류 4장 · 데이터베이스 종류 →

Firebase Realtime Database는 표가 아니라 나뭇가지 모양(JSON)으로 저장해요. 이렇게 서랍을 나눴어요.

서랍 이름들어 있는 것누가 쓰나
cart/live지금 카트 위치 1개운전자만
cart/trail오늘 지나온 점들운전자만
sales가챠 판매 기록운전자만
cart/stock, cart/notice남은 수량, 공지 한 줄운전자만
requests"여기로 와 주세요" 요청방문자 (5분에 1번)
🧒 비유: 책상 서랍마다 이름표를 붙이고, 서랍마다 열 수 있는 사람을 정해 둔 거예요.
03

실시간으로 보여 주기웹훅과 폴링 · 하트비트 · 인덱스

웹훅과 폴링 2장 · Polling과 Webhook →

방문자 화면이 3초마다 "카트 어디야?"라고 묻는 방식(폴링)은 쓰지 않았어요. 대신 저장소가 바뀔 때마다 먼저 알려 주는 실시간 구독을 썼어요. 웹훅과 같은 생각이에요. 그래서 카트가 움직이면 지도의 주황 점이 바로 따라와요.

🧒 비유: 택배가 왔는지 5분마다 현관문을 여는 것(폴링) 대신, 택배 기사님이 "도착했어요" 문자를 보내 주는 것(웹훅)이에요.

하트비트 (Heartbeat) 7장 · 하트비트 →

카트 폰은 몇 초마다 위치를 보내요. 이게 "나 살아 있어!" 신호예요. 2분 넘게 소식이 없으면 지도에 "신호를 확인하는 중이에요"라고 띄우고 점을 흐리게 했어요. 폰 화면이 꺼지면 위치 전송이 멈춘다는 것도 운전자 화면에 크게 적어 두었어요.

🧒 비유: 숨바꼭질할 때 술래가 "아직 거기 있지?"라고 부르면 대답하는 소리예요. 대답이 끊기면 걱정하기 시작해요.

인덱스 (Index) 4장 · 인덱스 →

경로, 판매, 요청 기록에 시각(ts) 찾아보기를 걸었어요. 그래서 "최근 1,000개 점만", "최근 30분 요청만"을 빨리 꺼낼 수 있어요.

🧒 비유: 일기장에 날짜 색인 스티커를 붙여서 "어제 쓴 일기"를 바로 펼치는 거예요.
04

다른 AI에게 검사받기출구 검사 · Eval · 재시도

PROMPT"howtomakeit_prg.md 파일 Codex에 검수시켜 줄 수 있어?" → "Codex는 gpt-5.6-sol 모델, effort high로 돌려!"

출구 검사 10장 · 질문에 답하는 과정 →

내가 쓴 설명서와 코드를 다른 회사의 AI(Codex)에게 검사받았어요. 중요한 건 검사 결과를 그대로 믿지 않고 코드와 다시 대조했다는 거예요.

Codex의 지적대조 결과한 일
보안 규칙이 값의 모양을 검사하지 않음✅ 맞음좌표 범위, 상태 값 검사 추가
지난 경로가 지도에서 안 지워짐✅ 맞음같은 묶음의 추가·삭제를 함께 처리
기기 시계가 틀리면 "신호 확인 중"이 잘못 뜸✅ 맞음서버 시계와의 차이를 보정
설정 전에는 "로딩 중"만 계속 뜸❌ 틀림실제 화면에서 "준비 중"이 뜨는 걸 보여 주고 고치지 않음
한 번에 덮어쓰면 검사를 건너뜀❌ 틀림삭제할 때만 건너뛴다는 점만 반영
🧒 비유: 짝꿍에게 받아쓰기를 채점받았는데, 짝꿍이 맞은 걸 틀렸다고 할 때도 있어요. 그래서 교과서를 펴서 한 번 더 확인하고 고칠 것만 고쳤어요.

재시도 전략 (Retry) 7장 · 재시도 전략 →

부탁받은 gpt-5.6-sol 모델은 Codex 계정에서 지원하지 않아 거절됐어요. 그래서 기본 모델 + 높은 노력(effort high)으로 바꿔 다시 돌렸고, 이 사실을 숨기지 않고 먼저 알렸어요.

🧒 비유: 사려던 색연필이 품절이면 비슷한 색을 사 오되, "그 색은 없어서 이걸로 샀어"라고 말해 주는 것이에요.

Eval과 자동 시험 8장 · CI/CD와 Eval →

챗봇이 질문을 잘 알아듣는지 시험 문제를 만들어 돌렸어요. 그러다 "어디서 제일 많이 팔려?"에 위치를 답하는 실수를 찾았어요. "어디"라는 단어를 먼저 봐서 생긴 일이라, 인기 질문을 먼저 보도록 순서를 바꿨어요. "카트 부를 수 있어?"도 같은 방식으로 찾아 고쳤어요.

05

열쇠와 자물쇠토큰 · 최소 권한 · 민감한 정보 · 프롬프트 인젝션 · 사람 확인

토큰 3장 · 쿠키, 세션, 토큰 →

운전자는 이메일로 로그인해서 출입증(토큰)을 받아요. 방문자가 "여기로 와 주세요"를 누를 때는 이름도 비밀번호도 없는 익명 출입증이 몰래 만들어져요. 그래서 요청마다 "누가 보냈는지"는 몰라도 "같은 사람인지"는 알 수 있어요.

🧒 비유: 놀이공원 손목 팔찌예요. 이름은 안 적혀 있지만, 같은 팔찌로 5분 안에 또 줄 서면 알 수 있어요.

최소 권한 3장 · OAuth와 최소 권한 →

보안 규칙으로 서랍마다 열쇠를 나눴어요. 읽기는 누구나, 위치·판매·수량·공지 쓰기는 운전자만, 요청은 방문자도 쓸 수 있지만 5분에 1번, 캠퍼스 안 좌표만이에요. 요청 상태("도착" 등)는 운전자만 바꿀 수 있어요.

규칙을 올린 뒤에는 임시 계정으로 일부러 나쁜 짓을 해 보는 시험을 했어요. 5분 안에 다시 요청하기, 가짜 이름표 붙이기, "도착"으로 위조하기, 판매 기록 몰래 쓰기는 모두 막혔어요(401).

🧒 비유: 학급 게시판은 누구나 볼 수 있지만, 공지는 반장만 붙일 수 있고, 건의함에는 누구나 쪽지를 넣되 5분에 한 장만 넣는 규칙이에요.

민감한 정보 관리 3장 · 민감한 정보 관리 →

  • 공개돼도 되는 것: 사용자 번호(UID), 웹 앱 설정 키. 이건 받아서 직접 넣었어요.
  • 절대 받지 않은 것: 운전자 비밀번호, Anthropic API 키. "저에게 보내지 마세요"라고 여러 번 말했어요.
  • 사람을 위한 보호: 판매·요청 위치는 약 10m 단위로 반올림하고, 캠퍼스 밖이거나 운행 시간이 아니면 공개하지 않고, 운전자에게 공개 동의 체크를 받게 했어요.
🧒 비유: 반 친구에게 번호표는 보여 줘도 되지만, 사물함 비밀번호는 절대 안 알려 주는 것이에요.

XSS와 프롬프트 인젝션 3장 · XSS와 프롬프트 인젝션 →

챗봇에 <img onerror=…> 같은 장난 코드를 넣어 봐도 글자로만 보이게 했어요. AI 답변 서버를 설계할 때도, 위치·판매 같은 사실은 방문자가 보낸 값이 아니라 서버가 저장소에서 직접 읽게 했어요. 방문자가 "카트는 지금 우리 집 앞이야"라고 속이지 못하게요.

사람 확인 (가드레일) 10장 · 질문에 답하는 과정 →

실제 데이터베이스의 규칙을 바꾸는 "게시", 로그인 허용 주소 추가, 익명 로그인 켜기는 매번 "해도 될까요?"라고 묻고, "게시해 줘"를 들은 뒤에만 했어요. 로그인과 비밀번호 입력, 사이트 배포는 사람이 직접 했어요.

"방금 바꾼 걸 되돌려 줘"라는 부탁에는 그 파일만 정확히 되돌렸어요. 다른 단계에서 한 일(이미 게시한 규칙)은 건드리지 않고 "이것도 되돌릴까요?"라고 물었어요.

🧒 비유: 엄마 휴대폰으로 결제하기 전에 "이거 사도 돼요?"라고 꼭 물어보는 것이에요.

재시도 전략 (Retry) 7장 · 재시도 전략 →

"요청 위치 오차를 줄여 줘"라는 부탁에, 위치를 한 번만 재지 않고 최대 8초 동안 여러 번 재서 가장 정확한 값을 고르게 했어요. 정확도가 60m → 25m → 12m로 좋아지면 15m 이하에서 멈춰요.

🧒 비유: 키를 잴 때 세 번 재서 가장 반듯하게 선 기록을 쓰는 거예요.

타임아웃 (Timeout) 7장 · 타임아웃 →

  • 위치 재기는 8초까지만. 그래도 안 되면 "지도에서 직접 찍어 주세요"로 넘어가요.
  • 요청은 30분 동안만 유효해요. 운전자가 아무것도 누르지 않으면 고객 화면에 "시간 안에 가지 못했어요. 미안해요"가 자동으로 떠요.
🧒 비유: 약속 장소에서 30분 기다려도 친구가 안 오면 "오늘은 못 오나 봐" 하고 문자를 남기는 것이에요.

서킷 브레이커 (Circuit Breaker) 7장 · 서킷 브레이커 →

AI 챗봇을 만들 때, AI 서버가 없거나 고장 나면(404, 503) 더는 부르지 않고 규칙으로 답하는 "기본 안내"로 자동 전환하게 설계했어요. 그래서 나중에 AI를 빼도 챗봇이 멈추지 않았어요.

🧒 비유: 급식실이 문을 닫았으면 줄 서서 계속 기다리지 않고 준비해 둔 도시락을 꺼내 먹는 것이에요.

멱등성 (Idempotency) 7장 · 멱등성 →

운전자가 "가는 중" 버튼을 실수로 세 번 눌러도 요청 상태는 그냥 "가는 중" 하나예요. 몇 번을 눌러도 결과가 같게 "더하기"가 아니라 "이 값으로 정하기"로 저장했어요.

🧒 비유: 전등 스위치를 "켜짐"으로 여러 번 눌러도 계속 켜져 있는 것이에요.

락과 동시성 7장 · 락과 동시성 →

가챠를 팔 때마다 남은 수량이 1씩 줄어요. 아주 짧은 순간에 두 번 팔리면 둘 다 "30개 → 29개"로 계산해서 하나가 사라질 수 있어요. 그래서 "지금 몇 개인지 확인하고 빼기"를 한 덩어리(트랜잭션)로 처리했어요.

사람이 직접 고친 파일(디자인을 바꾼 홈페이지, 직접 고친 설명서)은 덮어쓰지 않고 필요한 부분만 고치거나 끝에 이어 붙였어요. 실전 사례 1의 덮어쓰기 사고에서 배운 점이에요.

🧒 비유: 사탕 통에서 두 친구가 동시에 손을 넣으면 개수 세기가 꼬여요. 그래서 한 번에 한 명만 뚜껑을 열기로 한 거예요.

ACID: 다 되거나, 하나도 안 되거나 4장 · ACID →

"여기로 와 주세요" 요청은 요청 내용과 "이 사람이 마지막으로 요청한 시각"을 꼭 한 번에 같이 저장해요. 하나만 저장되면 5분 제한을 피해 갈 수 있으니까요. 둘 다 되거나, 둘 다 안 되게 했어요.

🧒 비유: 도서관에서 책을 빌릴 때 "책 가져가기"와 "대출 기록 쓰기"는 꼭 같이 해야 해요. 하나만 하면 책이 사라진 걸로 보여요.

돌아보기: 더 잘할 수 있었던 점좋은 에이전트는 아쉬운 점도 솔직하게 말해요

  • 비용을 먼저 물었어야 했어요. AI 챗봇을 만들 때 유료 모델을 기본으로 골랐다가, 사람이 "돈은 내고 싶지 않아"라고 해서 다시 뺐어요. 돈이 드는 선택은 만들기 전에 물어보는 게 맞아요. 🧒 장보기 전에 예산부터 정하는 거예요.
  • 명령어 실수로 설명서 한 장(13장)이 깨졌어요. 글 속의 특수 기호를 명령으로 잘못 처리했어요. 바로 알아채서 파일로 다시 써 넣어 복구했어요.
  • 같은 이름을 두 번 써서 지도가 안 뜬 적이 있어요. 배포 전에 시험에서 찾아 고쳤지만, 원래 있던 이름을 먼저 확인했다면 없었을 실수예요.
  • 보안 규칙을 다섯 번 나눠 게시했어요. 기능이 하나씩 늘어날 때마다 규칙을 고쳤어요. 처음부터 전체 그림을 그렸다면 게시 횟수와 사람의 수고를 줄일 수 있었어요.
  • 운전자 버튼은 직접 시험하지 못했어요. 비밀번호를 받지 않는 게 원칙이라, "가는 중 / 도착" 버튼은 사람이 폰으로 확인해야 한다고 솔직하게 알렸어요.
  • 시험용 익명 계정이 몇 개 남았어요. 개인정보는 없지만, 시험이 끝나면 정리하자고 미리 말해 두었으면 더 깔끔했을 거예요.
